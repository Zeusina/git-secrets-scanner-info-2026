# Git Secrets Scanner (gss)

*Читать на других языках: [English](README.md)*

Мощная консольная утилита для сканирования Git-репозиториев с целью обнаружения и идентификации потенциальных утечек конфиденциальной информации, таких как API-ключи, пароли, токены, данные для подключения к базам данных и другие секреты.

## Возможности

- **Комплексное обнаружение секретов**: Использует настраиваемые правила и регулярные выражения для идентификации различных типов секретов
- **Гибкие режимы сканирования**: Сканирование всей истории, последних N коммитов или конкретных веток
- **Настраиваемые правила**: YAML-конфигурация для пользовательских правил обнаружения
- **Опциональная валидация секретов**: Проверяет найденные секреты как active, inactive или error через HTTP или команды
- **Фильтрация по статусу валидации**: Позволяет скрывать inactive-секреты и ошибки валидации в отчётах
- **Фильтрация ложных срабатываний**: Встроенные фильтры для снижения количества ложных срабатываний
- **Множественные форматы вывода**: Генерация человекочитаемых текстовых или машиночитаемых JSON-отчётов
- **Чистая архитектура**: Модульная, тестируемая и поддерживаемая кодовая база
- **Полное покрытие тестами**: Включены модульные и интеграционные тесты

## Установка

### Требования

- Go 1.21 или новее
- `golangci-lint` (опционально, для линтинга)

### Сборка из исходного кода

```bash
# Клонировать репозиторий
git clone https://github.com/Zeusina/git-secrets-scanner-info-2026.git
cd git-secrets-scanner

# Собрать бинарный файл (Linux/MacOS)
go build -o bin/gss ./cmd/gss

# Собрать бинарный файл (Windows)
go build -o bin/gss.exe ./cmd/gss

# Бинарный файл будет находиться в ./bin/gss.exe (Windows) или ./bin/gss (Linux/macOS)
```

## Использование

### Базовое сканирование

Сканирование последних 10 коммитов текущего репозитория:

```bash
./bin/gss scan . --last 10 --output text
```

### Сканирование всей истории

```bash
./bin/gss scan /path/to/repo --all-history --output text
```

### Сканирование конкретной ветки

```bash
./bin/gss scan /path/to/repo --branch develop --output json
```

### Использование пользовательской конфигурации с абсолютным путём

```bash
./bin/gss scan . --config /custom_rules/rules.yml --output text
```

### Использование пользовательской конфигурации с относительным путём

```bash
./bin/gss scan . --config ./rules/custom-rules.yml --output text
```

### Параметры командной строки

```
Использование:
  gss scan <repo-path> [флаги]

Флаги:
  -c, --config string      Путь к файлу конфигурации правил (по умолчанию "config/rules.yml")
                           Поддерживаются как абсолютные, так и относительные пути:
                           - Абсолютный: C:\rules\custom.yml или /etc/gss/rules.yml
                           - Относительный: ./config/rules.yml или ../rules.yml
  -o, --output string      Формат вывода: text или json (по умолчанию "text")
      --all-history        Сканировать всю историю Git
      --last int           Количество последних коммитов для сканирования (по умолчанию 10)
      --branch string      Имя ветки для сканирования (по умолчанию: текущая ветка)
  -v, --verbose            Включить подробное логирование
  -h, --help              Показать справочную информацию
```

## Конфигурация

### Файл правил (config/rules.yml)

Правила обнаружения определяются в формате YAML:

```yaml
rules:
  - name: "Ключ доступа"
    pattern: 'AKIA[0-9A-Z]{16}'
    keywords:
      - "access_key"
    priority: "critical"
    min_length: 20

  - name: "Общий API-ключ"
    pattern: '(api[_-]?key|apikey)\s*[:=]\s*["\']?([a-zA-Z0-9]{32,})["\']?'
    keywords:
      - "api_key"
      - "token"
    priority: "high"
    min_length: 32
    validation:
      enabled: true
      timeout: "5s"
      retries: 2
      retry_delay: "1s"
      http:
        url: "https://api.example.com/validate?key={{secret}}"
        method: "GET"
        headers:
          Authorization: "Bearer {{secret}}"
        expected_status: 200

false_positives:
  keywords:
    - "YOUR_API_KEY_HERE"
    - "example_token"
  patterns:
    - '(demo|example|sample|test)'

excludes:
  - '.*_test\.go$'
  - '^test/'
  - '/fixtures/'
  - '/testdata/'
  - '/demo/'

hide_inactive_secrets: false
hide_validation_errors: false
```

### Поля правила

- **name**: Человекочитаемое название правила
- **pattern**: Шаблон регулярного выражения для поиска секретов
- **keywords**: Контекстные ключевые слова для сужения совпадений
- **priority**: Уровень серьёзности (low, medium, high, critical)
- **min_length**: Минимальная длина найденного секрета
- **validation**: Опциональная конфигурация валидации для проверки активности секрета
  - **enabled**: Включение валидации для правила
  - **timeout / retries / retry_delay**: Параметры выполнения валидации
  - **http**: Валидация HTTP-запросом (`url`, `method`, `headers`, `body`, `expected_status`)
  - **command**: Валидация выполнением команды (`command`, `args`, `expected_exit`, `inactive_exit_codes`, `expected_output`)

### Ложные срабатывания

Настройка фильтров ложных срабатываний для снижения шума:

- **keywords**: Ключевые слова, указывающие на ложное срабатывание
- **patterns**: Шаблоны регулярных выражений, которые должны быть отфильтрованы

### Исключения файлов

Настройка паттернов для исключения файлов и директорий из сканирования:

- **excludes**: Список регулярных выражений для путей файлов, которые следует пропустить
  - Полезно для исключения тестовых файлов, демо-кода и фикстур
  - Паттерны применяются к полному пути файла относительно корня репозитория
  - Примеры: `.*_test\.go$` (Go тесты), `^test/` (директория test), `/fixtures/` (фикстуры)
- **hide_inactive_secrets**: Если `true`, находки со статусом `validation_status=inactive` не попадают в отчёт
- **hide_validation_errors**: Если `true`, находки со статусом `validation_status=error` не попадают в отчёт

## Соображения безопасности

- Секреты маскируются в выходных отчётах (показываются только первые и последние 2 символа)
- Секреты не логируются в stdout (только в отчётах)
- Для валидации доступны таймауты и ретраи, чтобы снизить влияние нестабильных проверок
- Настраиваемые фильтры ложных срабатываний для предотвращения ненужных предупреждений
- Поддержка пользовательских паттернов игнорирования, аналогичных `.gitignore`

## Коды выхода

- `0`: Успех, секреты не обнаружены
- `1`: Ошибка при выполнении или обнаружены секреты

## Ключевые решения по дизайну

### Архитектура

- **Чистая архитектура**: Разделение ответственности с независимыми модулями
- **Интерфейсно-ориентированный дизайн**: Repository, Reporter и Detector реализованы как интерфейсы для тестируемости
- **Обработка ошибок**: Корректная обёртка ошибок и передача контекста
- **Поддержка контекста**: Все I/O операции поддерживают context для отмены и таймаутов

### Конфигурация

- **Правила на основе YAML**: Легко понять и модифицировать правила обнаружения
- **Регулярные выражения**: Мощное сопоставление паттернов для обнаружения секретов
- **Контекст через ключевые слова**: Наличие ключевых слов помогает сузить релевантные совпадения
- **Фильтры ложных срабатываний**: Снижает шум от значений-заполнителей и примеров

### Производительность

- **Скомпилированные регулярные выражения**: Паттерны компилируются один раз при инициализации
- **Пропуск бинарных файлов**: Игнорирует бинарные файлы для повышения производительности
- **Потоковая обработка**: Коммиты обрабатываются последовательно для управления памятью
